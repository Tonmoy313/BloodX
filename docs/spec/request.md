# request — create, upload, track (requester side)
Entities: BloodRequest(id, public_code unique e.g. A-1042, requester_user_id, client_request_id (unique per requester), hospital_id, ward_bed_note?, component, blood_group, urgency, bags_needed 1..6, needed_by_at, patient_name?, contact_phone (requester's verified phone at creation), requisition_slip_key?, status, bags_pledged, bags_donated, current_wave, boosted_until, created_at, closed_at, close_reason) · Hospital(id, name_en, name_bn, area_id, address, lat, lng, type, public_phone, is_verified, active) · UploadSlot(id, user_id, object_key, declared_content_type, declared_length, status, expires_at, created_at).
Indexes: BloodRequest unique(public_code), unique(requester_user_id, client_request_id), (status, urgency, needed_by_at), (hospital_id, status), (requester_user_id, created_at).
Endpoints: createRequest(component, group, bags, urgency, hospital_id, ward/bed, needed_by, patient name?, slip key?, client_request_id) · getUploadUrl(slip, content type, length) · confirmUpload(key) · getRequest · watchRequest(stream) · listMyRequests(status, cursor, limit) · extendRequest(new needed_by) · cancelRequest(reason).
Rules:
- Hospital from the seeded list only. needed_by in the future, ≤30 d. Urgency: <6 h CRITICAL, same day SAME_DAY, else SCHEDULED (requester may raise it). Whole blood only in v1 (other components → coming soon). Requester phone OTP-verified. Max 6 bags (more → admin), ≤2 active requests, 5 creates/24 h/phone. A requester cannot pledge to their own request.
- Extend re-runs waves from the current wave. Cancel notifies pledged donors. Replaying createRequest with the same client_request_id returns the original.
- Upload: client compresses first → getUploadUrl validates type/length against config and signs those exact values (10 min) into `pending/` → client uploads straight to R2 → confirmUpload checks the stored object (mismatch deleted, UPLOAD_INVALID) → createRequest attaches only a confirmed key owned by the same user. `pending/` objects deleted after 24 h (lifecycle + job). Store only the key. Slip deleted 90 d after the request closes. [Likely] A presigned URL cannot enforce single use or max size alone; the confirm step and lifecycle delete are the controls.
- Status screen: honest counts only (notified / viewed / pledged, elapsed time); no time estimate until real data exists (P-005). After 20 min with no pledge: show nearest blood banks + call option and flag admin. Share card (WhatsApp/Facebook): group, hospital, urgency, bags progress, deep link; NEVER a phone number.
Screens: S04 Home (greeting; "Needs your action" strip; Request blood CTA; tiles: Whole blood + others as coming soon; Active now: my request / my pledge; donor card; "See all history") · S06 step 1 (component, group chips, bags stepper, urgency) · S07 step 2 (debounced hospital search, ward/bed, needed-by, patient name, slip photo, ☑ share my number with donors who pledge — required) · S08 review/submit · S09 searching (hospital pin only, no donor positions; counts; elapsed; share; cancel) · S10 pledged list (first name + initial, arrival time, status, Call/WhatsApp via revealContact; "Still searching for N bag(s)"; released banner "X didn't confirm and was released. Searching again…"; extend; share).
Nav: bottom bar Home · Messages (coming soon) · Community (coming soon) · Profile; history lives under Profile.
Offline: queue submit, "not sent yet" banner, retry reuses client_request_id, never lose form input. Lists: skeleton loaders, keyset infinite scroll.
Tests: validation (hospital, bags, needed_by, rate limit) · idempotent replay · upload type/length mismatch rejected, unconfirmed can't attach, pending expires, slip retention · extend/cancel · keyset pagination stable while rows arrive · stream reconnect after Wi-Fi kill shows latest snapshot · presigned URL expiry mid-upload recovers.
